# android_vendor_der

Надстройка организации **der-exp** над прошивкой Android: движок маршрутизации
[steer](https://github.com/xyzmean/steer) и его обвязка под систему. Подключается из
`device.mk` устройства строкой `$(call inherit-product, vendor/der/config/der.mk)` после того,
как локальный манифест положил дерево в `vendor/der`.

Первая цель — DerpFest 16.2 (Android 16 QPR2) для Xiaomi beryllium (Pocophone F1), с заделом на
Android 17. Движок встраивается **на уровне системы, собранной из исходников**, без root и
Magisk.

## Что здесь есть

| Путь | Что это |
|---|---|
| `config/der.mk` | Продукт: пакеты `steer`, `nft` и `Splify2`, подключение политики SELinux, свойство-выключатель |
| `apps/Splify2/` | Приложение splify2 — экран управления движком (WebView + мост к сокету движка); договор частей — `BRIDGE.md` |
| `init/steerd.rc`, `init/Android.bp` | Сервисы init: управляющий сокет, помощники выходов, применение правил, резолвер dnsd, сторож, снятие правил при выключении |
| `sepolicy/public/steerd.te` | Объявления типов домена `steerd` и его файлов/сокета |
| `sepolicy/private/steerd.te` | Права демона и запреты, скрывающие движок от чужих приложений |
| `sepolicy/private/splify2_app.te` | Домен приложения splify2 — единственной двери к движку |
| `sepolicy/private/{file,property,seapp}_contexts` | Метки бинарников, данных, свойства и привязка приложения |
| `kernel/gki-android16-6.12/` | Ядро GKI 6.12 с nf_tables без нарушения договора с модулями производителя (первая цель — OnePlus 15T): правка, фрагмент, скрипт сборки со сверкой контрольных сумм |
| `manifest/beryllium.xml` | Локальный манифест: сводит устройство, ядро, блобы, nftables и vendor/der для `repo sync` |
| `tools/ndk-check/` | Проверка сборки модулей `Android.bp` компилятором NDK и запуск в aarch64-VM |
| `tools/sepolicy-check/` | Компиляция политики SELinux против настоящей `system/sepolicy` без полного дерева |
| `tools/app-check/` | Проверочная сборка APK splify2 инструментами SDK, без дерева платформы |

Собранные части userspace (порт nftables под bionic и сам движок) лежат в соседних
репозиториях: `android_external_libmnl`, `android_external_libnftnl`, `android_external_nftables`.
Сборка движка под Android описана файлом `Android.bp` в корне дерева steer: модули `steerd`
(движок, со ссылкой `steer-tools`) и `steer` (клиент сокета), умолчание платформы
`-DSTEER_DEFAULT_PLATFORM=android` — поле метки вне битов netd, пути `/data/misc/steer`, без
вызовов OpenWrt.

## Как steer скрыт от приложений

Изоляцию на Android даёт **домен SELinux, а не uid**. Домен `steerd` устроен так, что у любого
приложения (`appdomain`) нет ни одного разрешения на бинарник, данные, сокет и процесс движка,
а запреты `neverallow` в `steerd.te` фиксируют это на этапе сборки политики. Единственное
исключение — домен `splify2_app`, которому разрешён ровно один канал: подключиться к
управляющему unix-сокету. Через TCP на `127.0.0.1` канал не идёт осознанно — локальный порт
видно любому приложению, а сокет с меткой SELinux виден только тому, кому это позволено.

Полезный факт, снятый с базовой политики Android 16: приложениям **уже** запрещён дамп
интерфейсов через netlink (`neverallowxperm all_untrusted_apps domain:netlink_route_socket nlmsg
RTM_GETLINK`). То есть значительная часть того, чем детект ловит туннель, закрыта апстримом, и
нам не нужно ослаблять платформу ради этого.

## Управляющий сокет

Приложение splify2 говорит с движком только через unix-сокет `/data/misc/steer/steer.sock`. За
ним — демон `steerd daemon` (служба `steerd`), который по запросу исполняет короткий список
команд: `status`, `diag`, `explain`, `apply` и `check` со спекой в теле запроса, `reload`,
`put-file`, `list-files`, `rm-file`, `dns-log`, `vless-nodes`, `vless-probe`, `version`. Протокол (строка-команда и тело, ответ — строка JSON с
кодом, stdout и stderr), пределы и поля ответов — в `docs/ctl.md` дерева steer.

- **Демон поднимается при каждой загрузке**, независимо от `persist.der.steer.enabled`: через
  него приложение показывает состояние и сохраняет спеку и при выключенном движке (`apply` тогда
  только сохраняет спеку; правила демон поставит, когда init после включения скажет ему
  `steer reload`, а при загрузке — сам, если движок включён). Выключатель приложение
  ставит само — `set_prop(splify2_app, steerd_prop)`; домену движка писать его нельзя.
- **Сокет создаёт сам демон**, а не опция `socket` у init: та кладёт сокет в `/dev/socket`,
  который листает любой домен (`domain.te`), — имя движка увидело бы любое приложение. Метку
  `steerd_socket` ставит `type_transition` на имя `steer.sock`; права файла `0666`, пускает
  SELinux (`connectto` из приложений — только у `splify2_app`; на userdebug ещё `su`) и сам
  сервер.
- **Кого пускает сервер**: uid 0 и 1000; процесс в домене `splify2_app` у пользователя 0 — домен
  узнаётся у ядра (`SO_PEERSEC`), так что uid приложения нигде не нужен; остальным — отказ и
  строка `steer[warn] ctl: отказ` в журнале.
- **Пределы**: строка запроса 512 байт, тело спеки 1 МиБ, файла списка 16 МиБ, 5 с на то, чтобы
  запрос дошёл целиком, четыре запроса одновременно, у каждой команды свой срок.
- **Батарея**: при выключенном движке у демона нет ни одного таймера — он спит без срока до
  запроса по сокету; при включённом сроки сторожа — на `CLOCK_MONOTONIC`. Замер в Cuttlefish
  (steer 1.8, `voluntary_ctxt_switches` за минуту тишины): выключен — 0, включён — 2–8.
- **Перечитать спеку** (`reload`, и сам после удачного `apply`): демон перечитывает спеку и
  положение выключателя, супервизор сверяет помощников выходов и таблицу резолвера.

Отладка из `adb root shell`: `steer ctl status`, `steer ctl apply < spec.json`
(`/system_ext/bin/der/steer`).

## Приложение splify2

`apps/Splify2` — управляющий экран движка на телефоне (на роутере ту же роль играют LuCI и
rpcd). Модуль `Splify2` (`android_app`): `system_ext/priv-app`, платформенная подпись, пакет
`com.der.splify2` — тот, к которому `seapp_contexts` привязывает домен `splify2_app`.

Три части, которые пишутся отдельно; договор между ними — `apps/Splify2/BRIDGE.md`:

| Часть | Где | Что делает |
|---|---|---|
| Экран | `web/`, собранное — `assets/web/` | страница на `@andromeda/ui` в мобильной раскладке |
| Оболочка | `src/com/der/splify2/` (кроме `logic/`) | Activity с WebView, мост JS↔Kotlin, сокет движка, настройки Android, список приложений |
| Логика | `src/com/der/splify2/logic/` | модель настроек, сборка спеки, каталог списков, подписки, резервная копия |

Оболочка:

- **Страница** грузится из `assets/web/` по адресу `https://appassets.androidplatform.net/web/`
  (свой `shouldInterceptRequest`, без androidx); значки приложений — там же, `/icon/<пакет>.png`.
  Любой другой адрес WebView получает отказом, `file://` и `content://` выключены, ссылки наружу
  открываются в браузере. Тёмная тема — по системной (тема приложения DayNight).
- **Мост**: страница зовёт `SplifyBridge.call(id, method, argsJson)`, метод исполняется в пуле
  из четырёх потоков, ответ — `window.__splifyReply(id, replyJson)`, события —
  `window.__splifyEvent(name, payloadJson)`. Методы `engine.*`, `system.*`, `apps.list` —
  оболочки, остальные передаются логике (`logic.Dispatcher`).
- **Движок** — только через управляющий сокет (`EngineClient.kt`, протокол `docs/ctl.md` дерева
  steer). Выключатель — свойство `persist.der.steer.enabled`, его ставит само приложение; перед
  включением текущая спека сохраняется через `apply`.
- **Private DNS** (решение владельца): при первом запуске `private_dns_default_mode=off`; когда
  в применённой спеке есть доменные каналы на сам телефон и движок включён — режим человека
  запоминается и ставится `off`; когда их нет или движок выключен — запомненное возвращается.
  Если человек сам сменил режим, пока он был выключен приложением, его выбор не перебивается.
- **Фон**: одно задание JobScheduler раз в сутки при сети и не на исходе батареи (работу делает
  логика). Ни постоянных сервисов, ни получателей событий, ни будильников; смену сети приложение
  слушает только пока открыт экран.
- **Разрешения**: `INTERNET`, `ACCESS_NETWORK_STATE`, `QUERY_ALL_PACKAGES`,
  `RECEIVE_BOOT_COMPLETED` (задание переживает перезагрузку) и `WRITE_SECURE_SETTINGS` (Private
  DNS; белый список — `privapp-permissions-com.der.splify2.xml` в `system_ext/etc/permissions`).
  Резервная копия данных приложения в облако и перенос на другой телефон выключены: в модели
  лежат ссылки подписок с ключами доступа.

Файлы списков и подписок логика заливает в `/data/misc/steer/lists` командой сокета `put-file`
(путь в спеке — тот, что назвал движок в ответе), а после каждого применения убирает свои файлы,
на которые спека больше не ссылается (`list-files` + `rm-file`). Движок старше `put-file`
отвечает `unknown-command`, и применение со списками или подписками не проходит — экран получает
отказ `engine`; движок без `list-files`/`rm-file` просто оставляет старые файлы.

**Проверочная сборка без дерева**: `sh tools/app-check/build.sh` — kotlinc против `android.jar`
SDK 36.1 (скрытый `SystemProperties` — заглушкой только для компилятора), aapt2, R8 с
`proguard.flags`, подпись тестовым ключом; в конце — сверка `aapt2 dump badging` (пакет, SDK,
ровно задуманный набор разрешений), dex (методы моста пережили R8, заглушки в dex нет) и
содержимое APK (страница `assets/web` и её бандл на месте, исходников экрана и стенда нет).
Логика и экран — настоящие: логику отдельно гоняет `sh tools/app-check/logic-test.sh` против
хостовой сборки движка (его `ctl-serve` на временном сокете, файловые команды — настоящие), экран
собирается `npm run build` в `apps/Splify2/web`. На телефоне (POCO F1, DerpFest 16.2) приложение
работает; в Cuttlefish (`products/`) — нет: WebView там только для arm64.

## policycap netlink_xperm (задел на Android 17)

В ядрах 6.13+ политика может включить возможность `netlink_xperm`: тогда сообщения netlink
проверяются правом `nlmsg` со списком типов (`allowxperm … nlmsg`), а не парой
`nlmsg_read`/`nlmsg_write`. Домен `steerd` без своего списка остался бы с одними `RTM_GET*` от
`netdomain` и не смог бы поставить ни `ip rule`, ни маршрут выхода, ни адрес TUN. Список для
`netlink_route_socket` уже стоит в `sepolicy/private/steerd.te` (link, addr, route, rule — то,
что зовут `ip` и сторож); без возможности он ничего не меняет, а ядро 4.19 POCO F1 её не знает.
`netlink_netfilter_socket` (nftables, ctnetlink) списков не требует: ядро проверяет типы
сообщений только у route, tcpdiag, xfrm и audit.

`tools/sepolicy-check/check.sh` собирает политику и с включённой возможностью (шестая строка
`ok` на вариант) и проверяет, что список `steerd` в ней есть. Включать её в прошивке — строкой
`policycap netlink_xperm;` в `system/sepolicy/private/policy_capabilities` (правка платформы;
ядро beryllium 4.19 её всё равно проигнорирует).

## Решения владельца и что осталось

1. **splify2 — на платформенной подписи.** Привязка в `seapp_contexts`: пакет
   `com.der.splify2`, `seinfo=platform`, `isPrivApp=true`, домен `splify2_app` (образец —
   `traceur_app`). Приложение — `apps/Splify2` (см. «Приложение splify2» выше).
2. **Невидимость — через маршрутизацию ядра, а не через ужесточение политики.** Движок работает
   метками пакетов, `ip rule` и nftables — без `VpnService`, без записи в ConnectivityService.
   Android и приложения ведут себя так, будто движка нет; платформенную политику для чужих
   приложений (`/proc/net/route`, `/sys/class/net`) не трогаем. RTM_GETLINK приложениям и так
   закрыт (см. выше).
3. **Дедицированный uid `AID_STEER`** вместо root у демона. Сейчас демон работает как root, но
   заперт доменом `steerd`; на Android это стандартно и изоляции не ослабляет, но uid — чище.
   Правка `android_filesystem_config.h`, отдельным коммитом.
4. **Помощники выходов со своим процессом** (`vless`/`xsteer`/`obfs`/`tgws`) держит супервизор
   демона (`steerd daemon --supervise`). Клиент VLESS входит в первую версию (решение
   владельца), mbedtls 3.6 — в `external/der-mbedtls`. zapret на телефоне не нужен.

## Батарея и сон (требование владельца)

Владелец поставил условием **низкое потребление в фоне и нормальный сон устройства**. Для
телефона это значит: движок не держит wakelock и не будит устройство таймерами, сторож выходов
проверяет их по событиям (смена сети, отказ трафика, включение экрана), а не по будильнику.
Сторож демона проверяет выходы по событиям ядра — смена интерфейса или адреса (сменилась сеть,
поднялся или упал туннель) запускает внеочередной проход — и по периоду для того, чего событием
не увидеть (туннель поднят, трафик не идёт). Ожидание и период — на `CLOCK_MONOTONIC`, который во
сне устройства стоит и не будит его; wakelock не берётся. Так же ждёт супервизор перед
перезапуском помощника. При выключенном движке таймеров нет вовсе. Включение экрана как событие
не отслеживается. Пробуждения процесса замерены в Cuttlefish (см. «Управляющий сокет»); сон
самого телефона с движком не мерился: на кабеле USB POCO не засыпает вовсе.

## Каналы на сам телефон и DNS

Кроме клиентов раздачи, канал может брать трафик самого телефона: в `from` — `"self"` (все
приложения, UID от 10000; системные демоны и сам движок идут напрямую) или `"uid:N"`/`"uid:N-M"`.
Правила стоят на хуке output и берут только соединения, которые приложение открыло само; канал
«весь трафик» не трогает свою сеть (RFC 1918, link-local, мультикаст), а IPv6 такого канала
отвергается — маршруты выходов только IPv4. На ядре 4.9 маршрут пересматривается цепочкой route
в таблице ip (`STEER_REROUTE_BIT` в `steer/src/spec.h`).

**masquerade** у выходов-интерфейсов (помеченный трафик раздачи и телефона уходит с адресом
туннеля) ставится правилом iptables первым в `nat POSTROUTING`, а не цепочкой nft: на старых
ядрах первая сработавшая регистрация nat решает судьбу соединения, и nft-цепочка рядом с NAT
netd либо не срабатывала бы, либо отнимала бы у netd раздачу. apply ставит, down снимает. netd
при перезапуске стирает правила, и демон, увидев пропажу своего `ip rule` 9000 (RTM_DELRULE),
возвращает `ip rule`, таблицы выходов и masquerade сам — в Cuttlefish за 1–5 с.

**DNS.** Резолвер движка на телефоне переспрашивает тот сервер, к которому запрос шёл до
заворота (адрес из conntrack, умолчание платформы android), ответ — с того адреса, на который
пришёл запрос; переспрос — с меткой сети исходного запроса (`SO_MARK`), по UDP и TCP, по IPv4 и
IPv6. При доменных
каналах на сам телефон заворачивается UDP/53 всех, включая root — DnsResolver шлёт запросы
приложений от root, — кроме собственных запросов резолвера (они помечены значением «сам движок»).

Что не покрыто:

- **Private DNS (DoT, порт 853)** — запросы по TLS резолвер не видит. Решение владельца:
  Private DNS не должен включаться сам, оркестрация — в splify2 (`apps/Splify2`, см. «Приложение
  splify2»; на устройстве не проверена).
- В образе нет `curl`/`wget`: скачивание подписок и списков — дело приложения.

**Журнал**: stdout и stderr служб идут в kmsg (`stdio_to_kmsg`) — строки `steer[warn]` и
`steer[info]` видны в `dmesg`.

## Статус проверки политики

Политика компилируется против `system/sepolicy` и `device/lineage/sepolicy` ветки lineage-23.2
скриптом `tools/sepolicy-check/check.sh`, для вариантов user и userdebug:

- с включённой `policycap netlink_xperm` — вся политика и список `nlmsg` у `steerd` (см. выше);
- все `neverallow` платформы, Lineage и наши — `checkpolicy` над policy.conf, собранным так же,
  как модуль `sepolicy_neverallows` (те же каталоги, порядок файлов и `-D`);
- половина system_ext отдельно — `checkpolicy -C` и `secilc`, как при сборке split-политики;
- метки в `*_contexts` ссылаются на объявленные типы;
- `seapp_contexts` — `check_seapp` платформы с её neverallow и сверкой по готовой политике;
- `sepolicy_tests` платформы над готовой политикой.

`checkpolicy` и `secilc` — из AOSP `external/selinux` (android-16.0.0_r4): в политике Android 16
есть то, чего не знает checkpolicy 3.5 из Ubuntu 24.04 (первый же отказ — `policycap
functionfs_seclabel`; дальше идёт `allowxperm … nlmsg`, бэкпорт AOSP поверх libsepol 3.7). Как их собрать, скрипт
подсказывает сам, если не находит.

Чего проверка не покрывает: политику производителя (`device/qcom`, sdm845-common) — её нет без
полного дерева; `treble_sepolicy_tests` (сравнение с прошлыми версиями API); настоящие значения
флагов выпуска (в скрипте включены все — с выключенными базовая политика не компилируется).
Поведение политики на устройстве не проверялось нигде.
